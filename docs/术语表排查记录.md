# 排查记录：术语表「看起来不生效」

## 现象

导入术语集（如 `transformer → 变压器模型`）后翻译，产出 PDF 里**完全找不到**强制译名，
但换个页码/换个调用方式又时好时坏。

## 排查过程与三个坑

### 坑 1：验证脚本读错了半边（我自己的 bug）

对照版是「左原文 + 右译文」拼版。最初用整页 `get_text()` 统计，把**左半边原文**也算进去了——
于是 `Transformer` 显示出现 52 次，看着像"术语表没生效"，其实是把英文原文当成了译文。
→ 修正：只统计 `x > 页宽 × 0.45` 且含中文的行。

### 坑 2：翻译缓存会掩盖术语表的差异

上游 `TranslationCache` 的缓存键 = `(translate_engine, translate_engine_params, original_text)`，
而 `translate_engine_params` 里的 `prompt` 注册的是**空文本的模板**（`self.prompt("")`），
**不包含每个批次实际拼进去的术语表内容**。
→ 同一页先用「不带术语表」翻过，再用「带术语表」翻，可能直接命中旧缓存，表现为术语表无效。
→ 验证术语表时务必换页码，或清掉 `~/.cache/babeldoc/cache.v1.db`。

### 坑 3（真凶）：上游「自动术语提取」与用户术语表冲突

即使前两个坑都排除，术语表**仍然不生效**。实测对照：

| 配置 | 变压器模型 | 注意力机制ZT | 编码器ZT | 解码器ZT |
|---|---|---|---|---|
| 只给用户术语表（自动提取默认开启） | 0 | 0 | 0 | 0 |
| **同上 + 关闭自动提取** | 2 | 5 | 3 | 3 |

上游默认会在翻译前**自己提取一份术语表**并注入提示词（`auto_extract_glossary`，默认 True）。
两份术语表同时存在时，用户指定的强制译名会被上游自动提取的结果压过。

→ **修法**：只要用户显式选了术语集，就自动传 `no_auto_extract_glossary=True`，
让用户的术语说了算。想两者都要可以加 `--keep-auto-glossary`（不推荐，会冲突）。

## 最终验证（走服务端 API，第 2 页）

```
[术语表] 已加载 1 个术语集（并关闭上游自动术语提取以避免冲突）
  变压器模型        5 次
  注意力机制ZT      3 次
  编码器ZT          3 次
  解码器ZT          3 次
结论: 术语表生效 ✅ (4/4)
```

## 给使用者的提示

1. 术语表**匹配大小写不敏感、空白归一、长词优先**（上游用 hyperscan 扫描）。
2. 术语表 CSV 必须有 `source,target` 表头（本工具会自动补齐/归一化，也支持 TSV、箭头、粘贴）。
3. 想确认术语表是否生效：在产出 PDF 里搜你的强制译名；若为 0，先换一页再试（避开缓存）。
4. 术语表条目越具体越好：`attention` 这种泛词容易与上下文冲突，建议写成完整术语。
