# 排查记录：译文「该换行的地方没换行」

现象（用户截图）：第 7 题原文是
```
7. Identify the variable of interest to the researcher.
   a) The textbook cost of first-year UM students.
   b) The year in school of UM students.
   c) The age of UM students.
   d) The cost of incidental expenses of UM students.
```
译文却变成一行：`7.确定研究者感兴趣的变量。a) 澳大一年级学生的教材费用。b) 澳大学生的年级。c) …`

---

## 逐层排查结论

| 层次 | 观察 | 结论 |
|---|---|---|
| 版面解析 | 原文 4 个选项各占一行（y 间隔约 14.6pt，与题干间隔 26.7pt 一致） | 解析阶段把「题干 + 4 个选项」合并成**一个段落** |
| 上游切分开关 | `split_short_lines` + `short_line_split_factor` 取 0.8 / 0.5 / 0.2 各跑一次 | **都无效**。该开关按「行宽 < 页内行宽中位数 × 系数」判定，等宽选项不触发 |
| 送入模型的文本 | dump 出真实提示词（见 [证据-发给模型的真实提示词.txt](证据-发给模型的真实提示词.txt)）：`"input": "7. Identify the variable of interest to the researcher. a) … b) … c) … d) …"` | 段落内部的换行**在进入模型前就已经没了**（整段字符按间距拼成一个串，只插空格） |
| 上游提示词 | 模板里写明：`Do NOT merge paragraphs, split paragraphs, or move content between paragraphs.` | 模型即使猜到原本分行，也被这条规则**明确禁止拆分** |
| 提示词补丁 | 给模板加「行结构例外」规则 + 在每个段落输入里按选项标记插入真换行，再跑 | 模型侧能看到行了，但**最终 PDF 仍然合并** → 问题不在提示词层 |
| 输出解析 | `output_unicode = translated_text`（原样保留，未吞换行） | 换行在解析阶段是存在的 |
| **排版（重排）层** | 同一页 A/B：补丁开/关，产出**完全一致**（都是 23 行、5 行含多选项） | **BabelDOC 的 typesetting 会把译文重新折行填回原段落的文本框**，模型输出多少换行都不影响最终版面 |

## 一句话根因

> 版面解析把多行选项合成一个段落，而 BabelDOC 的重排是按「段落」这个粒度重新折行的；
> 只要它还是一个段落，译文就不可能保留原来的行边界。**必须在「段落」这一层拆开，而不是在文本或提示词层。**

## 已试方案与结果

| 方案 | 结果 |
|---|---|
| `split_short_lines` / `short_line_split_factor`（0.2/0.5/0.8） | ❌ 不触发（宽度判定对等宽选项无效） |
| 翻译器代理：把清单段落逐行调 API、用 `\n` 拼回 | ⚠️ 规则与代理单测通过（6/6），但被重排层抹平 → 无效 |
| 提示词注入「行结构例外」+ 段落文本插换行 | ⚠️ 同上，A/B 完全一致 → 无效 |
| 让翻译在主进程跑（`basic.debug=True`）以支持打补丁 | ⚠️ 补丁能生效，但产出带 debug 标注、且**取消任务失效** → 不能作默认 |
| **IR 层拆段**：包装 `ParagraphFinder.process_page`，按行拆成多个 `PdfParagraph` | ❌ 补丁传不进子进程（见下节） |
| **预处理源 PDF**：清单块按行拆开 + 拉开行距 | ❌ 实测更差：并行行数 5 → 8（行距 ×1.5 时为 6） |

## 为什么「打补丁」这条路走不通（关键发现）

pdf2zh-next 把版面解析与翻译放在 **multiprocessing spawn 子进程**里，子进程是全新解释器：

| 传递机制 | 结果 |
|---|---|
| 父进程改模块属性（给 `ParagraphFinder.process_page` 打补丁） | ❌ 子进程 import 上游时重新绑定原函数，覆盖补丁 |
| `multiprocessing.util.register_after_fork` | ❌ spawn 模式不触发 |
| 替换子进程入口 target（`_translate_wrapper`） | ❌ 需 pickle：闭包报 `Can't get local object`；改模块级函数后子进程重新 import 会重置 `__main__` 状态 |
| `sys.addaudithook` 捕获 spawn 事件 | ❌ 子进程里不触发 |
| 环境变量 + `PYTHONPATH` + `sitecustomize.py` | ❌ 仍未生效 |
| 垫片包（site-packages 放同名模块，导入期打补丁） | ⚠️ 机制可行，但等于改上游文件，升级即失效 → 不算低风险 |

实测证据：在 `install()` 与 `process_page` 里写 PID 探针，多轮运行中**只有父进程 pid 出现过**。

## 结论：没有「低风险且有效」的解法

- 想真正修好 → 必须改上游（垫片包 / 直接改 site-packages 里的 `paragraph_finder.py`），或长期开 `debug=True`（有副作用）；
- 想保持低风险 → 只能接受现状。

因此默认配置**不做任何补丁**，只在 README「已知限制」里如实说明。
三份实验代码保留备查、默认关闭：`webapp/ir_split.py`、`webapp/list_split.py`、`webapp/line_structure.py`。

## 可行的下一步（需要选一条）

1. **在中间表示层拆分段落**（推荐）：在版面解析之后、翻译之前，把「清单式段落」
   按行拆成多个段落块，让每个选项成为独立段落。重排时它们各自占一个文本框，
   行结构自然保留。风险：多个小段落需要更多纵向空间，字少的页面可能被挤到续页。
2. **改上游重排代码**：让 typesetting 识别译文里的 `\n` 并按原始行盒对齐。
   改动深、与上游分支差异大，后续升级容易冲突；上游明确不鼓励直接改内部实现。
3. **换输出形态**：只用 BabelDOC 产「仅译文」页，再由我们按原文几何自己合成对照版。
   控制力最强，但要重写对照排版（此前那版 Node 方案就是干这个的）。
4. **接受现状**：把「清单类文档行结构不完美」写进已知限制。

> 提示：这类多选题在 `2002_Ch1 Handout.pdf` 这类讲义里很常见，但普通论文正文段落
> 大多是连续长句，**不会**出现这个问题——影响面主要是"题目/选项、条目清单"类版面。
